# xz_visit_stats v2.0.0 数据库迁移设计方案

> 状态：**迁移草案，待依据 v1.3 真实数据基线重新评审。**
>
> 继续数据库设计前必须读取 `docs/v2.0.0/v1.3-data-baseline.md`，并由本机 Codex 工作区对现有 v1.3 数据库执行只读数据画像。未经该步骤，不得把本文件中的新增表规划视为最终方案。

## 目标

v2.0 在保持 v1.3 数据兼容的基础上扩展分析能力，不直接重构旧访问记录表，采用增量数据库升级方式。

升级原则：

- 不删除旧表
- 不破坏已有访问数据
- 升级过程可重复执行
- 支持失败回滚
- 新安装与旧版本升级使用同一套结构检查逻辑

# 重新评审顺序

1. 读取 v1.3 真实表结构与采集代码；
2. 对本机现有 v1.3 数据执行只读画像；
3. 确定哪些指标直接从原始日志查询即可；
4. 确定哪些高频指标需要小时/日汇总表；
5. 确定页面统计的稳定维度（Path / 规范化 URL / Z-Blog 内容 ID）；
6. 确定来源、错误是否值得单独落表，避免重复保存原始日志已有事实；
7. 再生成最终 migrate 方案。

# 升级流程

1. 检测当前插件/数据库版本；
2. 只创建正式 PRD 已确认的结构；
3. 保留原访问日志；
4. 初始化必要配置；
5. 迁移可重复执行；
6. 执行 v1.3 → v2.0 本机真实升级验证；
7. 核对历史统计结果与升级前基线。

# 性能要求

v2.0 不允许每次访问产生大量附加数据库写入。优先考虑从原始日志增量汇总、缓存和定时/惰性计算，而不是为每个分析模块同步写一份重复事件数据。

# Codex开发约束

1. 不根据旧设计文档猜测 v1.3 字段；
2. 数据画像只读，不修改现有日志；
3. 不删除旧字段或旧表；
4. 所有迁移增加幂等保护；
5. 数据模型冻结前不得继续扩张旧 Smart Analytics 表；
6. 完成后必须执行本机真实升级和数据库验证。
