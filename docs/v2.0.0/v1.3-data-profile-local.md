## 2. 真实数据库与日志表确认

Z-Blog 配置实际使用 MySQLi，数据库前缀为 `zbp_`。通过 `INFORMATION_SCHEMA.TABLES` 确认当前 v1.3 日志表为：

`zbp_xz_visit_stats_log`

不是仅依据 `inc/install.php` 推断。当前日志表为 MyISAM，真实 schema 如下：

- `zbp_xz_visit_stats_pages`：1 行，数据 44 B，索引 2 KiB。

任务中特别点名的 `xz_visit_pages`、`xz_visit_keywords`、`xz_visit_errors`、`xz_visit_security`（按当前前缀即 `zbp_xz_visit_*`）均未发现。不能把它们当作现有表，也不能依据名称假设它们应该保留。

现有索引：`PRIMARY(vs_ID)`、`xzvs_visited_at(vs_VisitedAt)`、`xzvs_visitor_time(vs_VisitorHash,vs_VisitedAt)`、`xzvs_bot_time(vs_IsBot,vs_VisitedAt)`、`xzvs_ip_time(vs_IP,vs_VisitedAt)`、`xzvs_status_time(vs_StatusCode,vs_VisitedAt)`。

## 8. 性能观察

对当前真实表执行 `EXPLAIN`：

- 仅按 `vs_VisitedAt` 过滤的计数使用 `xzvs_visited_at`，当前扫描 132 行。
- 按时间过滤后按 `vs_Path` 聚合显示 `Using temporary; Using filesort`，没有可用 Path 索引。
- 按时间过滤后按 `vs_Referer` 聚合显示 `Using temporary; Using filesort`，且 Referer 为 TEXT，不适合直接建立完整索引。
- 按 Bot/Status 聚合的样本查询也显示临时表和 filesort；当前行数很小，暂无实际压力，但数据增长后会放大。

建议在正式迁移前用生产规模压测验证候选索引，而不是仅凭本机 132 行决定。候选方向是时间+Path 前缀复合索引、有限长度的来源域名/来源类型字段，以及日/小时汇总表；不要直接为 TEXT 原字段建立全值索引。

## 9. v2.0 数据设计判断

### A. 可继续由 v1.3 原始日志计算

- 总访问量、按时间范围访问量和日趋势。
- VisitorHash 去重访客数（需明确 masked IP 不改变现有 hash 口径）。
- IP 去重数，但只能作为当前隐私模式下的记录值统计。
- Path/Url 基数、Top Path、访问来源域名级聚合。
- Referer 直接/站内/外部/搜索/社交的近似分类。
- 状态码分组、404 数量、平均和分位耗时。
- Browser、OS、Device 的非空覆盖率及基础分布。
- 普通访问与蜘蛛访问、BotName 分布（当前样本为零，但字段已存在）。

### B. 建议放入小时/日汇总表

- 小时/日 PV、VisitorHash UV、IP UV。
- 小时/日 2xx/3xx/4xx/5xx/404。
- 小时/日蜘蛛 PV、蜘蛛 UV、BotName。
- 小时/日 Top Path、来源类型和搜索引擎分布。
- 小时/日平均耗时及可追溯的耗时分桶；如要精确 P95/P99，应保存可合并的 histogram/quantile sketch，而不是只保存平均值。

当前只有 132 行，原始日志计算仍足够；汇总表的必要性来自未来增长和后台查询稳定性，不是当前样本的性能证明。

### C. 需要新增采集字段

- 可靠的搜索关键词：仅凭当前 Referer 域名无法稳定得到关键词，且现代搜索引擎通常不提供。
- 站内文章/页面 ID：只存 Path/Url 会受别名变化影响。
- 明确的来源类型、来源域名规范化结果：避免每次从 TEXT Referer 解析。
- 请求方法、响应字节数、协议/客户端地址族等更细粒度性能与安全指标。
- 安全事件所需的规则命中、事件类型、风险级别、处置结果。
- 若要做会话/停留时长，需要会话标识、首末事件或前端心跳；当前 VisitorHash 不能单独推出这些指标。

### D. 历史数据不足、不能可靠追溯

- 历史搜索关键词及关键词排名/转化。
- 历史安全事件、攻击类型、规则命中和处置结果。
- 历史会话数、跳出率、停留时长、页面序列。
- 可靠的蜘蛛抓取覆盖率与 BotName 趋势：当前样本蜘蛛为零。
- 生产级长期趋势、同比/月环比和容量曲线：本机只有两个活跃日期。
- 精确的历史耗时分布合并：当前可以对原始日志重算，但未来若只保留均值则不可追溯。

### E. 应删除或降级的指标

- “关键词分析”在没有可靠关键词采集前应降级为“搜索引擎来源”，不要用 Referer 猜测伪关键词。
- “安全分析”在没有安全事件字段前应降级为状态码/异常请求概览，不应伪装成安全检测结果。
- 蜘蛛分析在无 Bot 数据时展示明确的“暂无样本”，不要生成趋势性结论。
- 依赖完整 URL 的统计应降级为 Path 统计，并继续禁止输出 query string。
- 仅有平均耗时而没有分布数据时，不应展示貌似精确的 P95/P99。

### F. Phase 1 表的保留、修改、删除判断

| 表 | 实际状态 | 建议 |

| `xz_visit_keywords` | 不存在；现有 `xz_visit_stats_keywords` 为空 | 暂不作为核心表；只有在确定关键词来源和隐私口径后再设计。 |
| `xz_visit_errors` | 不存在 | 当前错误数可由日志状态码计算，暂不单独建表；若要记录错误详情，应先明确事件模型和保留周期。 |
| `xz_visit_security` | 不存在 | 暂不创建；当前日志不足以支撑安全事件模型，先补采集字段与规则定义。 |

## 10. Data Model Findings 重新评审

以下判断同时依据 v2.0 的“站长访问分析中心”定位、当前功能范围和本机 v1.3 真实数据；“保留”表示保留为经修改后的能力，不表示按旧字段原样创建。

### A-I 明确结论

| 项目 | 判断 | 原因 |
|---|---|---|
| A. `xz_visit_pages` | 修改；不按旧名称原样保留 | 页面分析是 v2.0 核心，但页面 PV/UV/错误/耗时事实已有原始日志来源。应改为带稳定页面键、时间粒度、唯一约束的页面汇总模型；优先评审现有 `xz_visit_stats_pages`，不重复建立事件表。 |
| B. `xz_visit_keywords` | 删除旧规划，关键词能力降级/后置 | 当前 v1.3 没有独立关键词字段，`xz_visit_stats_keywords` 为空；产品文档也不承诺完整关键词排名。首发只保留搜索引擎来源，未来有可靠可解析关键词时再设计小范围事实表。 |
| C. `xz_visit_errors` | 删除独立错误表规划 | 2xx/3xx/4xx/5xx/404 和错误 URL 都能从原始日志得到；错误分析是 v2.0 核心页面，但首发应直接查询日志或使用日汇总，避免重复保存 URL、Referer、UA。只有出现独立错误事件生命周期时再另行设计。 |
| D. `xz_visit_security` | 删除并移出 v2.0 首发 | 当前产品范围明确移出实时安全告警、自动封禁和复杂风控；现有日志没有风险规则命中、风险等级或处置结果，不能靠迁移表制造安全能力。 |
| E. 小时汇总表 | 需要，作为趋势/性能层；不是本次立即迁移 | 最近 7/30 天趋势、小时 PV/UV/IP、蜘蛛和错误分布适合汇总。当前 132 行不足以证明压力，但现有 EXPLAIN 已显示聚合会产生 temporary/filesort，应为可配置或惰性构建的小时层预留设计。 |
| F. 日汇总表 | 需要，优先级高于小时表 | 日汇总是稳定的长期查询层，适合 PV/UV/IP、状态码、蜘蛛、来源类型和页面摘要，也支持原始日志按保留周期清理后继续看长期趋势。 |
| G. 继续直接使用 `xz_visit_stats_log` | 明细、详情和低频/自定义查询 | 访问记录筛选、最近 5/15/30 分钟、单条完整 UA/Referer/URL 详情、错误最近记录、蜘蛛最近记录、任意回溯范围的精确重算，以及没有对应汇总维度的临时查询继续使用原始日志；展示时仍遵守隐私和 query string 规则。 |
| H. v1.3 不足、不能历史回算 | 真实新/回访、稳定 Session、跳出/停留/漏斗、完整关键词排名、安全事件与处置、被关闭采集期间的 Referer/UA/蜘蛛、脱敏 IP 原值、可靠历史页面标题 | 这些限制由 v1.3 字段和配置决定，不能通过迁移补回；应标注“仅升级后统计”或从首发移出。 |
| I. 需要返工的 Phase 1 schema/migration | `xz_visit_stats_pages`、`xz_visit_stats_page_uv`、`xz_visit_stats_keywords` 以及迁移目标命名/粒度都要返工；不创建 `errors/security` 旧表 | 当前三表已写入本机，但 pages/page_uv 只有 1 行且缺少稳定唯一模型，keywords 为空；现有升级代码把它们作为 2.0 目标，不能直接视为最终 schema。迁移应改为只创建正式确认的日/小时汇总和页面汇总结构，并保持幂等、保留原始日志。 |

### 汇总表建议的最小方向

- 日汇总：日期 + PV/VisitorHash UV/IP UV + 人类/蜘蛛 + 状态码分类 + 404/5xx + 耗时分桶或可合并分布摘要。
- 小时汇总：小时 + PV/UV/IP + 人类/蜘蛛 + 状态码分类；页面、来源、Bot 维度按查询成本和容量决定是否拆分子表。
- 页面汇总：稳定页面键（优先 Z-Blog 内容 ID，无法解析时使用规范化 Path）+ 日期/小时；不得仅依赖无唯一约束的 TEXT URL。
- 关键词：不进入首发迁移；来源分析保留搜索引擎和域名级聚合。
- 错误：首发直接来自日志/汇总，不复制完整 Referer/UA/URL 到错误表。
- 安全：不进入首发 schema，待后续明确事件模型和采集字段。

## 11. 推荐基线

- 统计口径：PV 以日志行计；UV 优先使用 VisitorHash；IP UV 明确标注受 full/masked 隐私设置影响；时间统一按站点时区展示，数据库保存 Unix 时间。
- 原始日志：建议保留可配置的 90 天或 180 天，汇总数据独立保留；实际周期应结合磁盘和合规要求确认。本机样本不足以证明具体周期。
- 汇总粒度：日汇总作为默认稳定层，小时汇总用于最近 7/30 天趋势；页面/来源/状态/Bot 维度都应带日期或小时键。
- 新索引：优先验证 `vs_VisitedAt + Path 前缀`、来源类型字段和汇总表唯一键；不要直接索引 TEXT Referer/Url 全值。
- 是否需要新汇总表：需要，原因是未来后台聚合会遇到临时表和 filesort；当前数据量小，不代表可以跳过设计。
- Phase 1 是否返工：需要。现有三张 `xz_visit_stats_*` 表的粒度、唯一性、页面键和来源/关键词模型尚未闭合；应先重写迁移设计，再开发实现。本次仅更新评审结论，不改数据库 schema。
