# V3-T2 本机 100k / 1m Benchmark

日期：2026-08-25

## 测试边界

- 使用本机现有数据库中的独立 benchmark 表。
- 未向真实 `xz_visit_stats_log` 写入数据。
- 未执行 `CREATE DATABASE` / `DROP DATABASE`。
- benchmark 表在每轮结束后删除；最终确认不存在。
- 数据为脱敏合成数据，覆盖 30 天、真人/蜘蛛、多 VisitorHash/IP、热门与长尾 Path、来源类型、状态码和 DurationMs。
- 每个查询执行 3 次；报告同时记录中位数和最大观察值。中位数主要反映 warm-cache，最大值用于提示较冷缓存风险。

## 数据规模与写入

|规模|基础索引写入|覆盖索引写入|说明|
|---:|---:|---:|---|
|100,000|约 6.5 秒|约 18.8 秒|覆盖 VisitorHash/IP、时间+来源/Path/耗时索引后写入变慢|
|1,000,000|约 607.7 秒|约 1,257.3 秒|覆盖索引写入成本明显，不推广到真实日志表|

## 核心查询结果

以下为第二轮覆盖索引 benchmark 的中位数 / 最大观察值；最大值不是生产 SLA，只用于识别冷缓存和高基数风险。

|查询|100k|1m|EXPLAIN 结论|
|---|---:|---:|---|
|Dashboard 30d|0.54 / 57.57 ms|0.45 / 4,640.74 ms|大范围聚合可能 ALL；真实 Dashboard 应优先走汇总|
|30d 趋势|0.34 / 286.20 ms|0.32 / 5,053.58 ms|时间索引命中，GROUP BY 使用 temporary/filesort|
|小时汇总读取|0.37 / 0.75 ms|0.63 / 2.37 ms|小时表 PRIMARY range，稳定|
|物化来源聚合|1.08 / 359.94 ms|0.45 / 8,796.87 ms|时间+来源覆盖索引命中，但仍 temporary/filesort|
|页面 Top N|0.43 / 828.64 ms|0.19 / 48,635.13 ms|时间+Path 覆盖索引命中，但长尾 GROUP BY/filesort 风险明显|
|Keyset 分页|0.20 / 0.73 ms|0.07 / 3.03 ms|PRIMARY range，稳定|
|精确 UV|0.48 / 1,806.31 ms|0.46 / 48,221.13 ms|真人+时间+VisitorHash 覆盖索引命中；高基数仍昂贵|
|精确 IP|0.29 / 274.34 ms|0.23 / 38,525.86 ms|覆盖索引可命中，但高基数仍昂贵|
|状态码趋势|0.52 / 6.92 ms|0.25 / 521.79 ms|状态+时间索引命中，GROUP BY temporary/filesort|
|慢请求页面|0.79 / 423.58 ms|0.39 / 45,034.04 ms|长尾页面聚合风险明显|

查询均完成，无 SQL 错误、死锁或数据损坏。查询返回行数符合预期：趋势 31 行、小时 721 行、来源 7 组、页面 Top 20、Keyset 50 行、状态 3 组。

## 索引决策

未向真实日志表新增索引。benchmark-only 覆盖索引虽然改善了 EXPLAIN 的覆盖性，但使 1m 写入成本约增加一倍以上，且冷缓存下长尾聚合和精确 DISTINCT 仍可能达到秒级到几十秒级；机械增加索引会伤害前台 INSERT。

当前正式策略：

- 小时/日汇总承担常用趋势和时段读取；
- Keyset 继续使用主键范围；
- 多日 UV/IP 保持精确 DISTINCT，不累加日/小时 UV/IP；
- 来源、页面、慢请求的大范围冷查询保留高基数风险说明；
- 千万级复杂聚合不承诺毫秒级。
